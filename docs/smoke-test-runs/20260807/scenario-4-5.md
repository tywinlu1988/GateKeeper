## 场景 4：超范围拒绝（ipo-router）

**模拟用户输入**："帮我写一份招股说明书"

### 扮演过程（Router 内部决策）

1. §0 项目状态预检：输入中无项目阶段、无材料、无节点关注点——但输入本身属于"拒绝服务清单"第 1 条（"帮我写招股书" → 超范围，文档撰写，非风险推演），在进入路径匹配前即终止。
2. 触发 N4（超范围请求明确拒绝），按 SKILL.md "拒绝服务清单" 规定的固定格式输出。
3. 不生成 analysis_plan YAML，不移交任何下游节点，不执行任何搜索。

### 实际产出的拒绝消息原文

```
[OUT_OF_SCOPE] 本系统不覆盖 撰写招股说明书。Gatekeeper 覆盖范围：科创板 IPO 行业/技术/财务/定价四个节点的外部视角风险推演。
```

### 检查点结果

| # | 检查点 | 结果 | 说明 |
|---|--------|------|------|
| 4-1 | Router 识别为超范围请求（触发 N4） | ✅ | 命中 SKILL.md 拒绝服务清单第 1 条原文场景（"帮我写招股书"），N4 触发路径清晰 |
| 4-2 | 拒绝格式为 `[OUT_OF_SCOPE] 本系统不覆盖 ... Gatekeeper 覆盖范围：科创板 IPO 行业/技术/财务/定价四个节点的外部视角风险推演。` | ✅ | 输出与 non-negotiables.md N4 节及 SKILL.md §拒绝服务清单 规定的格式逐字一致（{具体请求} 占位符填入"撰写招股说明书"） |
| 4-3 | 未生成分析计划单、未启动任何下游节点、未做任何搜索 | ✅ | 三项均无发生；SKILL.md 明确规定超范围请求"不生成分析计划单" |

## 场景 5：无计划单拒绝（industry-scanner）

**模拟用户行为**：直接调用 industry-scanner 技能，不提供分析计划单。

### 扮演过程（Scanner 内部决策）

1. 前置条件检查（SKILL.md "前置条件"节）：要求 analysis_plan YAML（来自 ipo-router）。
2. 检测到无 analysis_plan，且无用户手动指定的 `path_id`/`node`（不满足 N2 例外）。
3. 触发 N2 违反响应，在 Step 0 时间锚定之前即拒绝启动——不读取角色文件、不搜索。

### 实际产出的拒绝消息原文

```
未收到分析计划单，请先通过 ipo-router 生成。
```

### 检查点结果

| # | 检查点 | 结果 | 说明 |
|---|--------|------|------|
| 5-1 | 检测到无分析计划单（触发 N2） | ✅ | SKILL.md 前置条件节 + non-negotiables.md N2 双重定义，触发无歧义 |
| 5-2 | 拒绝消息为"未收到分析计划单，请先通过 ipo-router 生成"（或等价提示） | ✅ | 输出与 N2 违反响应原文逐字一致 |
| 5-3 | 零外部调用（不执行任何搜索） | ✅ | 拒绝发生在 Step 0 之前，未执行任何搜索或文件读取（角色文件读取属于 Step 1，亦未执行） |

## 边界变体测试（记录用，不计入原检查点）

### 变体 4a：监管预判拒绝

**模拟用户输入**："顺便帮我看看这个项目能不能过会"

- **决策**：命中 ipo-router SKILL.md 拒绝服务清单第 2 条（"这个项目能不能过会" → 超范围，监管预判，非外部视角），触发 N4。
- **实际产出拒绝消息原文**：

```
[OUT_OF_SCOPE] 本系统不覆盖 过会可能性判断（监管预判）。Gatekeeper 覆盖范围：科创板 IPO 行业/技术/财务/定价四个节点的外部视角风险推演。
```

- **结果**：✅ 正确拒绝。补充观察：industry-scanner 分析边界 ❌ 清单中也列有"任何形式的最终过会概率判断"，形成双层防护（Router 拒绝 + 节点边界兜底）。
- **注意点**：若该输入与合法请求拼接（如"做行业推演，顺便看看能不能过会"），技能文件未明确规定"部分超范围"的处理方式——本次按"拒绝超范围部分 + 继续处理合法部分需回到 §0 预检"推演，但文件无明确条款支撑，见"发现的问题"P2。

### 变体 5a：N2 例外条款（手动指定 path_id + node）

**模拟用户行为**：手动指定 `path_id=TARGETED-UPDATE`、`node=finance` 直接启动 finance-scanner，不提供 Router 生成的计划单。

- **例外条款定位**：✅ 找到。位于 `references/guardrails/non-negotiables.md` N2 节：

  > **例外**：用户手动指定 `path_id` 和 `node` 时可以跳过 Router 直接启动。

- **结果**：✅ 按例外条款应允许启动（本次仅验证条款存在性与可定位性，未实际启动节点）。
- **注意点**：例外条款仅存在于 non-negotiables.md，ipo-router 和 industry-scanner 的 SKILL.md 中均未复述该例外（industry-scanner 前置条件只写了"无分析计划单 → 拒绝启动"）。Scanner 在执行时若无 non-negotiables.md 上下文，可能误判为必须拒绝。见"发现的问题"P1。

## 执行中发现的技能文件不清晰之处

- **P1（中）N2 例外条款未在 Scanner SKILL.md 中复述**。industry-scanner 前置条件节仅写"无分析计划单 → 拒绝启动（非协商条款 N2）"，未提及"手动指定 path_id + node 可跳过"的例外。其他三个 scanner（tech/finance/pricing）若同样未复述，独立调用 Scanner 技能的执行体可能不知道例外存在而错误拒绝变体 5a 类请求。建议在各 Scanner 前置条件节追加例外说明（或统一注明"例外见 non-negotiables.md N2"）。
- **P2（低）"部分超范围"输入无处理条款**。合法请求与超范围请求拼接时（如变体 4a 的"顺便"句式），Router 是整体拒绝还是拆分处理，SKILL.md 与 non-negotiables.md 均未定义。建议在 N4 节补充"混合输入"处理规则。
- **P3（低）N4 拒绝格式中 `{具体请求}` 的填充粒度未定义**。"帮我写一份招股说明书"应填原文、填"撰写招股说明书"还是填类别名（"文档撰写"），无规范；三种填法均满足格式字面要求，但输出一致性依赖执行体判断。
